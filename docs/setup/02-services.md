## 1. Generate secrets for `.env`

We need three random strings. Two are for Django/JWT (Checkpoint 3 uses them) and one is the Postgres password.

```bash
python3.11 -c 'import secrets; print(secrets.token_urlsafe(50))'  # DJANGO_SECRET_KEY
python3.11 -c 'import secrets; print(secrets.token_urlsafe(50))'  # JWT_SIGNING_KEY
python3.11 -c 'import secrets; print(secrets.token_urlsafe(24))'  # POSTGRES_PASSWORD
```

> **Important:** the two 50-character secrets MUST be different from each other. Reusing the same secret across Django's session signing and JWT signing weakens both — if one leaks, both break.

> Why `secrets.token_urlsafe()`? It uses Python's cryptographically secure RNG (not the regular `random` module) and outputs URL-safe characters (no `/`, `+`, `=`) so the string can sit anywhere — env files, URLs, headers — without escaping.

Save all three outputs in a temporary scratchpad. You'll paste them into `.env` in step 3.

## 2. Create `docker-compose.yml`

This file lives at the **project root** (alongside `.env.example`, `.gitignore`, `README.md`).

```yaml
# ─── RANGER V3: Development services ───
# Runs PostgreSQL + Redis only. Django and React run natively for hot reload.
# Stop with: docker compose down
# Wipe data: docker compose down -v   (deletes volumes)

services:
  postgres:
    image: postgres:16-alpine
    container_name: ranger_postgres
    restart: unless-stopped
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    container_name: ranger_redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  postgres_data:
  redis_data:
```

### What each piece does

- **`image: postgres:16-alpine`** — Postgres 16 on Alpine Linux. Alpine = small image (~80 MB vs ~400 MB for the standard Debian-based tag). Same Postgres binary, minimal OS underneath.
- **`container_name`** — gives the container a fixed name instead of an autogenerated one like `rangerplatformv3-postgres-1`. Easier to reference in commands.
- **`restart: unless-stopped`** — if the container crashes (or you reboot), Docker auto-restarts it. The `unless-stopped` variant respects manual `docker stop` (won't restart until you `docker start`).
- **`environment`** — passes env vars from `.env` into the container. Postgres uses these to bootstrap the DB on first run.
- **`ports: "5432:5432"`** — maps host port 5432 → container port 5432. Django (running natively on host) connects to `localhost:5432` and traffic forwards into the container.
- **`volumes: postgres_data:/var/lib/postgresql/data`** — Docker named volume that persists the DB across container restarts. Without this, `docker compose down` would wipe your data.
- **`healthcheck`** — Docker probes the container with this command every 5s. If `pg_isready` returns success, the container shows `healthy`.

The Redis service is simpler: no env vars (Redis has no users/passwords by default in dev), and `redis-cli ping` is its health probe.

> **Note:** unlike older Compose files, modern Docker Compose doesn't require `version: "3.8"` at the top. The Compose specification handles it implicitly.

## 3. Create the real `.env`

`.env.example` is the template. `.env` is the real file with real values, and it's `.gitignore`d so it never goes to GitHub.

```bash
cd ~/projects/ranger-platform-v3
cp .env.example .env
code .env   # opens in VS Code
```

Replace the three `change-me` placeholders with the three secrets generated in step 1:

- `DJANGO_SECRET_KEY=` ← first 50-char secret
- `JWT_SIGNING_KEY=` ← second 50-char secret
- `POSTGRES_PASSWORD=` ← the 24-char Postgres password

Leave everything else default (`POSTGRES_DB=ranger_v3`, `POSTGRES_USER=ranger`, `REDIS_HOST=localhost`, etc.).

Save with `Ctrl+S`.

## 4. Verify `.env` is gitignored

Critical safety check before any commit:

```bash
cd ~/projects/ranger-platform-v3
git status
```

`.env` should **NOT** appear in the output. Only `docker-compose.yml` should be untracked.

Also explicitly:

```bash
git check-ignore -v .env
# Expected: .gitignore:5:.env	.env
```

That output confirms `.gitignore` line 5 is what's ignoring `.env`.

> **If `.env` ever shows up as tracked:** stop immediately. Don't commit. Fix `.gitignore` first. Committing real secrets to GitHub means rotating every secret afterward — a real headache.

## 5. Start the services

```bash
cd ~/projects/ranger-platform-v3
docker compose up -d
```

- `up` = start the services
- `-d` = detached mode (run in background, return your terminal)

First run pulls both images (~30 seconds). Expected output:

```
[+] Running 4/4
 ✔ Network ranger-platform-v3_default  Created
 ✔ Volume "ranger-platform-v3_postgres_data"  Created
 ✔ Volume "ranger-platform-v3_redis_data"  Created
 ✔ Container ranger_postgres  Started
 ✔ Container ranger_redis  Started
```

Wait ~10 seconds for healthchecks, then:

```bash
docker compose ps
```

Expected output (note the `STATUS` column shows `(healthy)`):

```
NAME              IMAGE                ...   STATUS                    PORTS
ranger_postgres   postgres:16-alpine   ...   Up 13 seconds (healthy)   0.0.0.0:5432->5432/tcp
ranger_redis      redis:7-alpine       ...   Up 13 seconds (healthy)   0.0.0.0:6379->6379/tcp
```

If you see `(starting)`, wait another 10s and re-run `docker compose ps`. If it stays `(starting)` for over a minute, check logs: `docker compose logs postgres` or `docker compose logs redis`.

> **If you see `permission denied while trying to connect to the Docker API`** — see [`troubleshooting/001-docker-permission-denied.md`](../troubleshooting/001-docker-permission-denied.md).

## 6. Functional tests

Healthchecks confirm the services *think* they're up. Manual tests confirm we can actually talk to them.

### Test PostgreSQL

```bash
docker exec -it ranger_postgres psql -U ranger -d ranger_v3 -c "SELECT version();"
```

Expected:

```
                                         version
------------------------------------------------------------------------------------------
 PostgreSQL 16.x on x86_64-pc-linux-musl, compiled by gcc (Alpine ...) ..., 64-bit
(1 row)
```

The exact patch version (16.6, 16.13, etc.) varies by image pull date — anything starting with `PostgreSQL 16.` is correct.

### Test Redis

```bash
docker exec -it ranger_redis redis-cli ping
```

Expected:

```
PONG
```

> **Tip — command name conventions:** Linux command names overwhelmingly use **hyphens**, not underscores. `redis-cli` not `redis_cli`. `pg_dump` is the rare exception (underscore is part of the binary name in Postgres-land). When in doubt, hyphen first.

### Test that volumes persist data

This proves a container restart doesn't wipe the database:

```bash
# Set a key
docker exec -it ranger_redis redis-cli SET test_key "hello-from-checkpoint-2"

# Restart the redis container
docker compose restart redis

# Wait, then read back
sleep 3
docker exec -it ranger_redis redis-cli GET test_key
# Expected: "hello-from-checkpoint-2"

# Cleanup
docker exec -it ranger_redis redis-cli DEL test_key
```

The value surviving a restart proves the volume mount works. If it returned `(nil)`, the volume isn't mounted correctly — check `docker-compose.yml`.

## 8. Reference: managing the services

Useful commands during day-to-day dev work:

```bash
# Start (detached)
docker compose up -d

# Stop (data persists)
docker compose down

# Stop and WIPE all data (nukes volumes — useful if migrations get tangled)
docker compose down -v

# View live logs
docker compose logs -f
docker compose logs -f postgres   # just postgres
docker compose logs -f redis      # just redis

# Status
docker compose ps

# Restart one service
docker compose restart postgres

# Open a psql shell
docker exec -it ranger_postgres psql -U ranger -d ranger_v3

# Open a redis-cli shell
docker exec -it ranger_redis redis-cli
```

## Things that went wrong (and how we fixed them)

### Issue: `permission denied while trying to connect to docker.sock`

**Symptom:** running `docker compose up -d` errors with `permission denied while trying to connect to the Docker API at unix:///var/run/docker.sock`.

**Cause:** the `docker` group membership added in section 6.3 of [`01-system-prep.md`](./01-system-prep.md) doesn't apply to existing terminal sessions. Linux loads group memberships at login.

**Fix:** full graphical logout and log back in. See [`troubleshooting/001-docker-permission-denied.md`](../troubleshooting/001-docker-permission-denied.md) for the full diagnostic flow.

### Issue: `docs/README.md` showed unexpected modifications

**Symptom:** after editing docs in VS Code, `git status` showed `docs/README.md` as modified even though I hadn't intentionally edited it.

**Cause:** when copy-pasting markdown content from chat into VS Code, the `cat > docs/README.md << 'DOCS_README_EOF'` heredoc wrapper around the markdown got pasted into the file as well.

**Fix:** remove the wrapper lines (first and last) from the file, or `git checkout docs/README.md` to discard local changes and accept the previously-committed version.

**Prevention:** when pasting code or markdown blocks from chat into a file, click *inside* the code fence first before selecting, or trim the first/last lines after pasting if any wrapper is visible.
